这个站的优化前版本还在线上：`/naive/`。你可以自己点开跑一遍 Lighthouse，和当前版本对比。**所有数字都是这么测出来的，不是估的。**

先给结论，再讲过程：

| | 优化前 | 现在 |
| --- | --- | --- |
| 首屏传输量 | 30,343 KiB | 1,097 KiB |
| Lighthouse Performance | 50 | 95（5 次中位数） |
| LCP | 7,810 ms | 750–1,190 ms |
| CLS | 0.436 | 0 |

一共十项改动。**前两项（图片转 WebP、加 `srcset`）拿走了 97% 的收益，后面八项加起来只降了 688 KiB。** 这个分布是我做完才知道的，做之前我以为脚本才是大头。

![首屏传输构成：慢版 30,377 KiB，快版 1,097 KiB](/images/tech/transfer-slow-vs-fast.webp)

## 第一步不是优化，是测量

优化前我先做了一件看起来很浪费时间的事：**把还没优化的版本打上 `v0-naive` 标签，冻结下来**。

理由是后面要拿它做对照。如果只留一个「优化后」的版本，那我说的「快了 96%」就永远是我自己说的，面试官没法验证。冻结之后，这个 tag 的构建产物可以随时重新部署一份，摆在旁边给人点。

然后是测量口径，这个比优化手段更重要：

1. **只测构建产物，不测 `pnpm dev`**。开发服务器不做压缩、不做 tree shaking，测出来的数字是假的。
2. **每次跑三遍，取中位数**。单次分数会跳，后面有图。
3. **冷缓存**。每次跑新建一个 Chrome 用户目录，跑完删掉。
4. **只测桌面**（`--preset=desktop`）。移动端我确实没测，这是这篇的边界。

测出来的第一版结果，按体积排完序，方向就清楚了：

| 类型 | 优化前 | 占比 |
| --- | --- | --- |
| 图片 | 29,886 KiB | 98% |
| 脚本 | 402 KiB | 1.3% |
| 样式 | 54 KiB | 0.2% |
| 字体 | 0 KiB | 0% |

**图片占了 98%。** 这意味着任何不碰图片的优化，天花板只有 2%。

## 前两项：97% 的收益都在这

### 一、全部转 WebP

21 张 JPG 一共 36.6 MB，用 `sharp` 转成 WebP（质量 80），变成 21.8 MB。

```js
await sharp(src)
  .webp({ quality: 80, effort: 6 })
  .toFile(dest)
```

只降了 40%。第一次看到这个数字我是失望的 —— 我以为 WebP 能省七成。后来才明白：**瓶颈不在格式，在像素量**。一张 3000×3750 的原图，就算用最先进的编码，它还是 3000×3750 的信息量。

### 二、`srcset` + `sizes`（这一项才是关键）

真正的问题在这一步暴露：**那张 3000px 宽的图，在页面上只占 325px 的格子。** 浏览器不知道这件事，它老老实实下载了 3000px 的版本。

```html
<img
  src="/images/photos/coast-10-1200.webp"
  srcset="/images/photos/coast-10-400.webp 400w,
          /images/photos/coast-10-800.webp 800w,
          /images/photos/coast-10-1200.webp 1200w"
  sizes="(max-width: 899px) calc(100vw - 48px), 325px"
  width="3000" height="3750"
  loading="lazy" decoding="async"
/>
```

两个属性各管一件事：

- `srcset` 告诉浏览器「这个文件名有多宽」
- `sizes` 告诉浏览器「我会把它显示成多宽」

浏览器拿这两个信息算出「我到底需要多宽」，再从候选项里挑最接近的。**关键是这个决定发生在 CSS 布局之前**，由预加载扫描器完成 —— 所以 `sizes` 写错，浏览器就挑错档位，而且不会等你布局完再改主意。

这一步的效果：18,166 KiB → 1,785 KiB。

## 中间四项：一个真收益，两个零收益，一个修 bug

### 三、懒加载 —— 桌面省 0 字节

给非首屏图片加 `loading="lazy"`，桌面端首屏传输量**一点没变**。

原因很实在：Chrome 的懒加载阈值大约是 1250px，而这个站首屏的 21 张图全在阈值以内，浏览器照下不误。只有在手机上（390×844）才真的生效 —— 实测只请求了 9 张。

**这条我照实写，因为它比「加了懒加载所以变快了」有用。** 知道一项优化在什么条件下无效，比知道它有效更难。

### 四、`width` / `height` —— 这一项修的是 CLS

CLS 从 0.436 掉到 0，靠的就是给每张图补上真实宽高，CSS 里配 `height: auto`。

这两个属性不是为了排版，是给浏览器一个提前量：图还没到，它就知道该预留多高。没有这个，图片下载完成后会把下面的内容往下推 —— 那个「推一下」就是 CLS。

副作用值得记：补上宽高之后，首屏图片请求数从 21 掉到 9。因为 banner 预留了 1290px 的高度，把首屏以下的图推出了懒加载窗口。

### 五、路由级代码分割 —— 首页省 0 字节

把所有非首页路由改成 `() => import()`，入口包从 403 KiB 降到 290 KiB。

但**首页的总传输量没变**，因为首页本来就需要那些代码（登录态、Supabase）。这一项的真实价值是「别的页面首屏更快」，不是「首页更快」。

### 六、Element Plus 按需引入 —— 这里省了 200 KiB

全站只用了 5 个组件（Button / Form / FormItem / Input / Pagination）。但原来的写法是 `app.use(ElementPlus)`，全量注册 80 多个组件 —— 一旦全量注册，tree shaking 就失效了，因为打包器无法证明「你没用到别的」。

改成逐个引入之后：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 入口 JS（压缩后） | 287.6 KiB | 90.1 KiB |
| 入口 CSS（压缩后） | 50.2 KiB | 14.6 KiB |

**估算库的体积，不要看 `node_modules` 有多大，要看你的入口包里它占了多少。**

## 后四项：都是小数，但都得做

- **七、图片质量收口**：题图单独降到 q68，全站编码 `effort` 从 4 拉到 6。图片 1,050 → 901 KiB。降质这件事我先做了 PSNR 对比（q80 是 34.29 dB，q68 是 32.21 dB），又裁了 1:1 的细节图肉眼看，确认看不出差别才动手。
- **八、把登录态挪出首屏包**：Supabase SDK 原来跟着首页加载（87 KiB）。改成按需异步加载后，脚本 193 → 143 KiB。代价是登录态有 100 ms 左右的延迟，所以顶栏那块要预留固定宽度，否则 CLS 会回来。
- **九、预加载**：给首屏关键的 chunk 加 `modulepreload`。这一项我在本地做了对照实验（开/关各跑三次），关掉时 LCP 中位数从 1,237 ms 变成 1,423 ms。
- **十、原图移出 `public`**：仓库里那 21 张原始 JPG（35.7 MB）浏览器从来没下载过，但它们一直在部署产物里。移出去之后部署体积从 69 MB 降到 33.8 MB。**这一项不改任何 Lighthouse 指标**，改的是发布体积 —— 说它「提升了性能」是不诚实的。

## 为什么分数不能只写一个数

同一份代码、同一台机器，连跑五次：

![冷缓存连跑五次的分数分布](/images/tech/perf-score-runs.webp)

慢版 38–52 分（中位 46），快版 94–97 分（中位 95）。

**区间本身就是结论的一部分。** 我在简历上写的是「Performance 95」，但心里知道它的含义是「94 到 97 之间，中位 95」。如果面试官当场跑出一个 92，我不该慌 —— 那在正常波动内。

这条经验后来救过我一次：某一项优化做完，分数从 97 掉到 94，我差点以为自己改坏了。查下来是 JS、CSS、请求数一个没变，图片还小了 149 KiB —— 那 3 分就是噪声。

## 三项「托管层」的东西我没算进成绩

有几项经常出现在性能优化的清单里，但这个站上我没法量化，所以**不算成绩**：

1. **CDN**：GitHub Pages 本身就是 CDN，没有「开」和「不开」两个版本可比。
2. **HTTP/2**：同上，托管方固定开启。
3. **缓存策略**：`Cache-Control` 由 GitHub Pages 决定，我改不了。

文档里这三条的写法是「—（托管层，无基线）」。**没有基线的优化，就没有资格写进成绩单。**

## 如果重来一次，我会这么排

1. 先冻结一个「优化前」版本（不然永远没法自证）
2. 先量，按体积排序，别猜
3. 打最大的那头，打到打不动为止
4. 每改一项就测一次，否则你不知道是哪一项起了作用
5. 把「没起作用」的那几项也记下来

第 5 条是这篇存在的理由。**大部分性能优化文章只写有效的部分，读者照做之后发现没效果，就以为是自己做错了。**
