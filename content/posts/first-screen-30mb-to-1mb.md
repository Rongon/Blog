这个站做过一轮完整的性能优化，一共十项改动。首屏传输量从 31.1 MB 降到 1.1 MB，Lighthouse 的 Performance 从 50 到 95。

优化前的版本还在线上（`/naive/`），点开可以直接对比。

先给结论：

| | 优化前 | 现在 |
| --- | --- | --- |
| 首屏传输量 | 31.1 MB | 1.1 MB |
| Performance | 50 | 95（5 次中位数） |
| LCP | 7,810 ms | 750–1,190 ms |
| CLS | 0.436 | 0 |

前两项（图片转 WebP、加 `srcset`）拿走了 97% 的收益，后面八项加起来只降了 0.7 MB。这个分布我是做完才知道的 —— 动手之前我以为脚本才是大头。

![首屏传输构成：优化前 31.1 MB，现在 1.1 MB](/images/tech/transfer-slow-vs-fast.webp)

## 第一步不是优化，是测量

动手之前，我先给当时的版本打了个 `v0-naive` 标签冻结下来。这样后面每改一项，都能把它和最新版本并排跑一遍，看这一项到底动了什么。

然后定测量口径，这部分比优化手段更影响结论：

1. **只测构建产物，不测 `pnpm dev`**。开发服务器不做压缩、不做 tree shaking，那里测出来的数字没有意义。
2. **每次跑三遍，取中位数**。单次分数会跳，后面有图。
3. **冷缓存**。每次跑新建一个 Chrome 用户目录，跑完删掉。
4. **只测桌面**（`--preset=desktop`）。这一篇的边界就到这里。

体积单位用十进制 MB（1 MB = 1000 KB）。Lighthouse 报告里显示的是 KiB（1 KiB = 1024 B），同一份数据换了个写法。

第一版报告按体积排完序，方向就清楚了：

| 类型 | 优化前 | 占比 |
| --- | --- | --- |
| 图片 | 30.6 MB | 98% |
| 脚本 | 0.41 MB | 1.3% |
| 样式 | 55 KB | 0.2% |
| 字体 | 0 KB | 0% |

图片占了 98%。这意味着不碰图片的优化，天花板只有 2%。

## 前两项：97% 的收益都在这

### 一、全部转 WebP

21 张 JPG，用 `sharp` 转成 WebP（质量 80），体积从 36.6 MB 变成 20.2 MB。

```js
await sharp(src)
  .webp({ quality: 80, effort: 6 })
  .toFile(dest)
```

只降了 45%，比我预期的少。原因后来才想明白：**瓶颈不在格式，在像素量**。一张 3000×3750 的原图，就算换成最先进的编码，它携带的信息还是 3000×3750 那么多。

### 二、`srcset` + `sizes`（这一项才是关键）

真正的问题在这一步暴露：**那张 3000px 宽的图，在页面上只占 325px 的格子。** 浏览器不知道这件事，它老老实实下载了 3000px 的版本。

```html
<img
  src="/images/photos/coast-10-1200.webp"
  srcset="/images/photos/coast-10-400.webp 400w,
          /images/photos/coast-10-800.webp 800w,
          /images/photos/coast-10-1200.webp 1200w"
  sizes="(max-width: 899px) calc(100vw - 48px), 325px"
  width="3000" height="3750"
  loading="lazy" decoding="async"
/>
```

两个属性各管一件事：

- `srcset` 告诉浏览器「这个文件名有多宽」
- `sizes` 告诉浏览器「我会把它显示成多宽」

浏览器拿这两个信息算出「我到底需要多宽」，再从候选项里挑最接近的。**这个决定发生在 CSS 布局之前**，由预加载扫描器完成 —— 所以 `sizes` 写错，浏览器就会挑错档位，而且不会等你布局完再改主意。

这一步的效果：18.6 MB → 1.8 MB。

## 中间四项：一个真收益，两个零收益，一个修 bug

### 三、懒加载 —— 桌面省 0 字节

给非首屏图片加 `loading="lazy"`，桌面端首屏传输量**一点没变**。

原因很实在：Chrome 的懒加载阈值大约 1250px，而这个站首屏的 21 张图全在阈值以内，浏览器照下不误。所以这一项在桌面端省了 0 字节。

知道一项优化在什么条件下无效，比知道它有效难。所以这条我照实记着。

### 四、`width` / `height` —— 这一项修的是 CLS

CLS 从 0.436 掉到 0，靠的是给每张图补上真实宽高，CSS 里配 `height: auto`。

这两个属性不是为了排版，是给浏览器一个提前量：图还没到，它就知道该预留多高。没有这个，图片下载完成后会把下面的内容往下推 —— 那个「推一下」就是 CLS。

副作用值得记：补上宽高之后，首屏图片请求数从 21 掉到 9。因为 banner 预留了 1290px 的高度，把首屏以下的图推出了懒加载窗口。

### 五、路由级代码分割 —— 首页省 0 字节

把所有非首页路由改成 `() => import()`，入口包从 403 KB 降到 290 KB。

但**首页的总传输量没变**，因为首页本来就需要那些代码（登录态、Supabase）。这一项的真实价值是「别的页面首屏更快」，不是「首页更快」。

### 六、Element Plus 按需引入 —— 这里省了 200 KB

全站只用了 5 个组件（Button / Form / FormItem / Input / Pagination）。原来的写法是 `app.use(ElementPlus)`，全量注册 80 多个组件 —— 全量注册之后 tree shaking 就失效了，因为打包器没法确认「你没用到别的」。

改成逐个引入之后：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 入口 JS（压缩后） | 295 KB | 92 KB |
| 入口 CSS（压缩后） | 51 KB | 15 KB |

要估一个库的体积，别看 `node_modules` 有多大，看你的入口包里它占了多少。

## 后四项：都是小数，但都得做

- **七、图片质量收口**：题图单独降到 q68，全站编码 `effort` 从 4 拉到 6。图片 0.92 MB，比上一版少 0.15 MB。
- **八、把登录态挪出首屏包**：Supabase SDK 原来跟着首页加载（87 KB）。改成按需异步加载后，脚本从 0.2 MB 降到 0.15 MB。代价是登录态有 100 ms 左右的延迟，所以顶栏那块要预留固定宽度，否则 CLS 会回来。
- **九、预加载**：给首屏关键的 chunk 加 `modulepreload`。本地做了开关对照（各跑三次），关掉时 LCP 中位数从 1,237 ms 变成 1,423 ms。
- **十、原图移出 `public`**：仓库里那 21 张原始 JPG（35.7 MB）浏览器从来没下载过，但它们一直在部署产物里。移出去之后部署体积从 69 MB 降到 33.8 MB。**这一项不改任何 Lighthouse 指标**，改的是发布体积。

## 分数不是一个固定值

同一份代码、同一台机器，连跑五次：

![冷缓存连跑五次的分数分布](/images/tech/perf-score-runs.webp)

优化前的版本 38–52 分（中位 46），现在 94–97 分（中位 95）。

**记下来的应该是区间加中位数，而不是某一次的好看数字。** 有一次某项改完，分数从 97 掉到 94，我差点以为改坏了。查下来 JS、CSS、请求数一个没变，图片还少了 0.15 MB —— 那 3 分是噪声。

## 三项「托管层」的东西我没算进这十项

有几项经常出现在性能优化清单里，但这个站上没法量化，所以没有算：

1. **CDN**：GitHub Pages 本身就是 CDN，没有「开」和「不开」两个版本可比。
2. **HTTP/2**：同上，托管方固定开启。
3. **缓存策略**：`Cache-Control` 由 GitHub Pages 决定，我改不了。

没有基线的优化，我不列为成绩。

## 如果重来一次，我会这么排

1. 先把「优化前」的版本冻结下来，不然没有回头对比的基线
2. 先量，按体积排序，别猜
3. 打最大的那头，打到打不动为止
4. 每改一项就测一次，否则不知道是哪一项起了作用
5. 把「没起作用」的那几项也记下来
