先给结论：**这个站点的首屏传输量里，图片占了八成以上**。所以在图片降下来之前，任何针对 JS 的优化都是在抠剩下的那两成。

下面按「先量、再改、改完再量」的顺序写，每一步都留了数字。

## 先测量，别猜

打开 DevTools 的 Network 面板，刷新，按体积排序。第一屏一共 1842 KB，其中：

| 类型 | 体积 | 占比 |
| --- | --- | --- |
| 图片 | 1509 KB | 82% |
| JS | 233 KB | 13% |
| CSS | 61 KB | 3% |
| 字体 | 61 KB | 3% |

这一步只需要花五分钟，但它决定了后面所有工作的优先级。

> 性能优化一定针对具体场景。同一套手段换一个站点，排序可能完全不同。

## 图片：收益最大的一项

四件事按这个顺序做，效果是叠加的：

1. 统一转 WebP，质量取 80，肉眼几乎看不出差别
2. 用 `<picture>` 保留原格式兜底，老浏览器不至于看到空白
3. 用 `srcset` + `sizes`，手机不会去下载桌面尺寸的大图
4. 非首屏图片加 `loading="lazy"`；反过来，首屏那张主图要标成 `fetchpriority="high"`

前三项是构建期就能做完的，第四项是属性，改起来最快。

```html
<picture>
  <source type="image/webp" srcset="/img/a-800.webp 800w, /img/a-1600.webp 1600w" sizes="(max-width: 900px) 100vw, 720px" />
  <img src="/img/a.jpg" alt="示例" width="1600" height="1067" fetchpriority="high" />
</picture>
```

注意 `width` 和 `height` 两个属性。它们不是为了排版，而是为了**让浏览器在图片下载完成之前就预留出正确的高度**，否则内容会被图片挤下去——这就是 CLS 的来源。

## 代码：收益中等，但面试官最爱问

- **tree shaking**：打包时删掉「引了但没用」的代码。它成立的前提是 ESM 的 `import` / `export` 是静态语法，不运行就能分析出来；CommonJS 的 `require` 是运行时求值，摇不掉。
- **代码分割**：动态 `import()` 是打包器唯一的分包信号。路由级懒加载就是用这个。
- **预加载**：`preload` 是「现在就要」，`prefetch` 是「以后可能要」。

这一项我踩的坑是：组件库如果全量引入，`tree shaking` 基本白做。改成按需引入之后，首屏 JS 从 1021 KB 降到 417 KB。

## 传输：三项，别抱太大期望

**缓存**要按文件特性分两类写：

```nginx
# 带内容 hash 的静态资源，一年不过期
/assets/*  Cache-Control: max-age=31536000, immutable
# 入口 HTML 必须每次回源验证，否则发新版用户看不到
/index.html Cache-Control: no-cache
```

**GZIP / Brotli** 只对文本有效。图片、字体、视频本身已经是压缩格式，再压一遍几乎没变化——这一项在别的站点可能收益很大，在图片为主的站点就是很小。

**HTTP/2** 的多路复用确实能解决队头阻塞，但它和 CDN 同时开启时，收益会互相抵消一部分，因为 CDN 已经把物理距离拉近了。

## 哪一项其实没用

如实记下来：

- **GZIP**：代码体积本来就不大，实测只快了 0.02 秒
- **CDN + HTTP/2 同时开**：相比只开 CDN，几乎没有提升

这两条反而比前面那些「有效」的更值钱——它们说明这一版的数字是测出来的，不是背出来的。
