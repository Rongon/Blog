这个仓库推一次代码，线上会更新两个站点：

| 路径 | 是什么 |
| --- | --- |
| `/Blog/` | 优化后，当前代码 |
| `/Blog/naive/` | 优化前，同一份源码关掉那十项优化 |

为什么要留着优化前：性能优化的结论是「从 A 变成 B」，只给你看 B 没有说服力。两个版本摆在同一个域名下，点开就能自己跑一遍。

下面是这条流水线里真正麻烦的地方 —— 都不是「怎么构建两次」这种问题。

## 优化前不是历史快照

最直觉的做法是：找到优化开始之前的那个提交，单独检出、单独构建、把产物放进 `/naive/`。第一版我确实是这么做的，用的 `git worktree` 检出那个 tag，然后在那个目录里单独 `pnpm install`。

它踩了三个坑，每一个都值得知道：

1. **tag 不在 checkout 里。** `actions/checkout` 默认只拉一个 commit，历史 tag 根本不在本地，得先 `git fetch --depth 1 origin tag v0-naive` 再 `worktree add`。
2. **两份 lockfile。** 那个时间点项目里还没有 `sharp`、`markdown-it`、`shiki`，依赖树完全不同，必须单独装一次。装错了不会报错，只会在运行时以一种莫名其妙的方式表现出来。
3. **字体目录不存在。** 字体是后来才加进项目的，那个版本的样式里已经写了 `@font-face`，目录却没有 —— 不补就会掉回系统字体，「同一份内容」的前提当场破掉。

这三个坑都填平之后，还有一个更根本的问题：**tag 里的文案停在优化前的那一天。** 后来首页标题改了、导航改了、项目页删了又加回来，tag 里全是旧的。

于是「优化后 vs 优化前」同时差着两样东西：性能和内容。读者看到两个页面长得不一样，第一反应是「这是两个站吧」，而不是「这是同一件事的两个版本」。

对照实验里，这叫做没控制住变量。

## 现在：同一份源码，换一个构建模式

优化前不再是一个历史快照，而是**同一个仓库用另一个 mode 构建**：

```bash
pnpm exec vite build --mode naive
```

`vite.config.ts` 里只多了一个 `naive` 分支，它做六件事，每一件都对应一项被关掉的优化：

| 关掉什么 | 怎么关 | 对应优化项 |
| --- | --- | --- |
| 路由级代码分割 | 换 `router/index.naive.ts`，所有页面静态导入 | 五 |
| Element Plus 按需引入 | 换 `plugins/element.naive.ts`，整包 `app.use(ElementPlus)` | 六 |
| 登录态异步加载 | `main.naive.ts` 启动时同步 `init()`，SDK 直接进入口包 | 八 |
| 响应式图片（srcset/sizes/懒加载/宽高） | 用 alias 把 `ResponsiveImage.vue` 换成 `ResponsiveImage.naive.vue`，一个 `<img>` + 原图 | 二、三、四 |
| WebP | 那个组件把 `.webp` 换回 `.jpg`，指回原图 | 一 |
| preload | 走另一个 HTML 入口，里面没有那两条 `<link>`；`base` 换 `/Blog/naive/` | 九 |

于是两版的差异只剩一件事：**优化加没加。** 页面上每个字、每个间距、甚至版本开关的位置，都是同一份源码渲染出来的。

代价也要说清楚：**不能再声称「这是当年真实的代码」。** 能声称的是「同一份源码，把这十项优化逐个关掉」。这个说法不如前者唬人，但它能站得住 —— 面试官真去比对两版页面，看到的东西是一致的。

## 开关不用注入

第一版优化前是 tag 的构建产物，源码一个字符都不能改，所以版本开关是**部署时注入**的：一个脚本把样式塞进 `</body>` 前，再插一段 HTML。

换成同一个 mode 之后，这件事自然消失了 —— 两版都是同一份源码，`VersionSwitch.vue` 本来就在里面，不需要注入，也不需要为了「让开关长得一样」去维护两套标记。

一句话：**能改源码的时候，别去改产物。** 注入产物是不得已时的办法，它天然脆弱（节点位置、样式作用域、SPA 接管时机），而且很容易让「两个版本只差性能」这句话变成假的。

## CI 里的步骤

一个 job 里跑完，顺序是：

1. `pnpm build --mode ghpages` —— 构建优化后，`base` 是 `/Blog/`
2. `cp dist/index.html dist/404.html` —— SPA 回退
3. `vite build --mode naive` —— 构建优化前，产物进 `dist-naive/`
4. `node scripts/copy-naive-images.mjs` —— 把原始 JPG 拷进慢版产物（它们不在 `public/` 下，否则会跟着主站发布）
5. 改入口文件名、复制慢版自己的 `404.html`，再把 `dist-naive/` 整体拷进 `dist/naive/`
6. `pnpm check:parity` —— 两版一致性检查，不一致就让这次发布失败

第 6 步是这条流水线里我最喜欢的一段：它用 runner 自带的 Chrome 把两个版本的每个页面打开，逐字比较静态文字，再在 390px 的手机视口下点一遍导航和菜单。

宁可不发，也不发一个「差异不只是性能」的对照版。

## 一个已知限制

GitHub Pages 只有**根目录**一份 `404.html` 会被拿来兜底。所以手输 `/naive/articles/xxx` 这种深链接时，落地的是主站的 404 页，由前端代码把地址送回 `/naive/`。

结果就是：从优化前首页点进文章没问题，但在文章页按 F5 会回到优化前首页。

值得修吗？要修就得让慢版改成 hash 路由（`/naive/#/articles/x`），那两版的路由形态就不一样了 —— 又回到「差异不只是性能」。这条我选择留着，写在文档里。

## 一句话

一次运行、一个产物、两个入口。麻烦的从来不是「构建两次」，是**让两个版本之间只剩一个变量**。
