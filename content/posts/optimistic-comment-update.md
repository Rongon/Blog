先说场景。评论区的常规写法是「悲观更新」：点发表 → 按钮转圈 → 等接口返回 → 成功了再把这条评论插进列表。

网络好的时候这没什么问题。但只要接口慢半拍，用户就会觉得「我点了但它没反应」，然后**再点一次**——于是同一条评论发了两遍。

乐观更新把顺序反过来：先认为它会成功。

## 真正的难点在哪

这件事本身不难，难的是三件收尾工作：

### 一、回滚要干净

失败时不能简单地 `pop()` 掉最后一条。因为在等待期间用户可能又发了别的评论，`pop()` 删掉的未必是刚才那条。

做法是**客户端临时 id**：发送前生成一个 `tmp-xxx` 挂在本地列表上；请求成功后用服务端返回的真实 id 替换掉它；失败时按这个临时 id 精确删除。

```ts
async function submit(text: string) {
  const tmpId = `tmp-${Date.now()}`
  list.value.push({ id: tmpId, text, pending: true })
  try {
    const created = await createComment({ text, clientId: tmpId })
    const i = list.value.findIndex((c) => c.id === tmpId)
    if (i > -1) list.value[i] = { ...created, pending: false }
  } catch {
    list.value = list.value.filter((c) => c.id !== tmpId)
    draft.value = text // 把用户打的字还回去，这是最容易被忽略的一步
  }
}
```

最后那行还回草稿很重要。如果失败了只是把评论删掉，用户打的字就白打了。

### 二、幂等与防重复提交

防重复要做两层：**界面上**请求进行中把按钮置灰；**数据上**同一个客户端 id 只接受一次创建。

第二层才是关键。界面上的防抖会被绕过——用户可能刷新页面、或者用两个标签页。

### 三、并发与顺序

「加载更多」会带来一个新问题：第 2 页的数据回来后，如果直接替换整个列表，会把还没同步到服务端的本地新评论冲掉。

做法是把**本地新增**和**远端返回**分开维护，合并时按 id 去重。这样翻页只影响远端那一份，本地那份不动。

## 面试官可能会问

**「失败之后用户打的字去哪了？」**
还回输入框了。这一点是刻意设计的：用户已经表达了意图，不该因为一次网络抖动就丢掉。

**「用户连点三次呢？」**
请求进行中按钮是置灰的，所以正常路径下点不出第三次。就算被绕过，同一个客户端 id 在服务端只会创建一条。

**「你怎么测试异常路径？」**
把 DevTools 的 Network 切成 Offline，或者用本地 mock 让它返回 500。异常路径不测，就等于没做。

**「为什么不用悲观更新？」**
因为它把网络延迟的成本转嫁给了用户。在评论这种「写入后不需要立刻拿到权威结果」的场景里，乐观更新的体验明显更好；反过来，涉及金额、库存这类场景就必须悲观。
