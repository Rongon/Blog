博客的评论区用的是「乐观更新」：点发表之后，评论立刻出现在列表里，请求在后台跑。

这个决定的理由很朴素 —— 网络只要慢半拍，用户就会觉得「我点了，它没反应」，然后**再点一次**。于是同一条评论发了两遍，而这本来是界面该解决的问题，不该让用户自己小心。

乐观更新把顺序反过来：先认为它会成功。

写到这里十分钟就够了。剩下的时间全花在收尾上。

## 先分清两个 id

这一块最容易讲错的地方，是代码里有两个长得像、作用完全不同的 id：

```ts
// 1. 本地临时 id：只活在浏览器内存里，用来在列表里「认出这条」
function makeTempId(): string {
  return `tmp-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`
}

// 2. clientId：幂等键，会写进数据库
const clientId = crypto.randomUUID()
```

- **临时 id** 不上服务端。它的唯一用途是：成功时知道该替换哪一行，失败时知道该删哪一行。
- **clientId** 会写进数据库。同一次「发表」如果重试，它保持不变，数据库靠 `(author_id, client_id)` 的唯一约束把重复的那次挡掉。

一开始我把这两个东西当成一个，用临时 id 去当幂等键 —— 结果刷新页面之后就失效了，因为临时 id 只活在内存里。

## 回滚不能 pop

失败时删掉最后一条是错的。因为在等待期间用户可能又发了一条，`pop()` 删掉的未必是刚才那条。

```ts
// 先上屏
comments.value = [optimistic, ...comments.value]
draft.value = ''

try {
  const saved = await createComment({ ...input, clientId })
  // 按临时 id 找位置替换，不是 pop
  const i = comments.value.findIndex((c) => c.id === optimistic.id)
  if (i > -1) comments.value[i] = { ...saved, pending: false }
} catch (err) {
  // 按临时 id 精确删除
  comments.value = comments.value.filter((c) => c.id !== optimistic.id)
  draft.value = text // 把用户打的字还回去
}
```

最后一行是重点，也是最容易漏的一行。失败了只是把评论删掉，用户打的字就白打了 —— 他会觉得这个功能在惩罚他。

## 幂等的坑：不是所有重复都是「唯一约束冲突」

这部分是我在这篇文章里唯一想强调的技术细节。

按直觉，重复提交会触发唯一约束，错误码 `23505`。所以只要把 `23505` 当成成功就行了。这里有个顺序问题，光看代码看不出来：

**数据库上的频率限制触发器是 `BEFORE INSERT`，它比唯一约束先执行。**

于是「同一条评论重试」拿到的很可能不是 `23505`，而是我们自己在触发器里 `raise` 的 `RATE_LIMITED`。用户看到的是一句「发得太快了」，但那条评论其实已经写进库了。他会以为失败，然后换一句话再发一遍 —— 评论区多了一条他以为没发出去的留言。

修法是：**出错时不管什么错，都先查一下这个 `client_id` 在库里是不是已经存在。**

```ts
if (error) {
  const { data: existing } = await supabase
    .from('comments')
    .select(COLUMNS)
    .eq('author_id', input.authorId)
    .eq('client_id', input.clientId)
    .maybeSingle()

  // 已经存在 → 说明上一次其实成功了，直接当成成功返回
  if (existing) return mapRow(existing)

  throw translateError(error)
}
```

代价是失败路径多一次查询。失败本来就是少数，这个代价可以接受；而「用户以为没发出去、其实发出去了」这种状态一旦出现，是没法自动纠正的。

## 防重复要做两层

1. **界面**：请求进行中按钮禁用 + loading。正常操作点不出第二次。
2. **数据**：同一个 `client_id` 只能创建一条。

第二层才是关键。第一层会被绕过 —— 用户刷新页面、开两个标签页、或者干脆用脚本刷。界面的约束是体验，数据的约束才是正确性。

## 翻页会把本地新评论冲掉

「加载更多」带来一个新问题：第 2 页的数据回来之后，如果直接替换整个列表，会把还没同步到服务端的本地新评论冲掉。

做法是把**本地新增**和**远端分页**分开维护，合并时按 id 去重。翻页只影响远端那一份，本地那份不动。这一块的代码比乐观更新本身还长。

## 怎么测异常路径

不测就等于没做。三个办法：

- DevTools 的 Network 面板切成 Offline，点发表。
- 用本地 mock 让接口返回 500。
- 断网状态下点发表，再恢复网络。

第三条看着像在测幂等，其实测不出来 —— 因为**用户主动重发时是新的 `clientId`**。

这里要说清楚幂等键到底防什么：它防的是「同一个请求被发出去两次」——浏览器或代理层重试、双击绕过了按钮禁用、两个标签页提交了同一份内容。它不防「用户看到失败之后主动再发一次」：在用户眼里那是第二条评论，系统里也应该是第二条。

把这两件事混起来，就会写出一个「重试复用旧 id」的实现，然后出现另一种 bug：用户改了错别字重发，结果什么都没发生 —— 因为被当成重复挡掉了。

## 什么场景不能乐观

乐观更新适合「写入之后不需要立刻拿到权威结果」的场景：评论、点赞、收藏、草稿。

反过来，涉及**金额、库存、名额**这类东西必须悲观 —— 先等服务端确认再显示。因为在这种场景里，「先显示成功再回滚」的代价不是一次体验不好，而是用户按错误的信息做了下一步决定。

判断标准一句话：**出错了能不能干净地退回去，且这个错误不会让用户做出错误的下一个动作。**
